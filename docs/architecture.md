# بنية كود BALANCE

## المبادئ

المشروع تطبيق متعدد الصفحات يعمل على استضافة ثابتة. هدف الفصل هو جعل المنطق قابلًا للفهم والاختبار مع الحفاظ على عناوين الصفحات ووظائفها، دون فرض إطار واجهة أو خادم بناء غير مطلوب.

اتجاه الاعتماد المفضل:

```text
HTML
  └─ page entry: ربط عناصر الصفحة والأحداث والحالة
       ├─ view/editor: HTML آمن وإدارة تفاعل محلي
       ├─ service: قراءة وكتابة عبر عميل مُمرّر
       └─ model/core: تحويل وفلاتر ودوال نقية
```

الدوال النقية لا تستورد `supabaseClient.js` أو `auth-guard.js` أو `shared.js`. تُمرَّر إليها القيم المطلوبة، وتُختبر دون `window` أو جلسة. يُفضّل أن تستقبل الخدمات العميل أو دوال الاتصال بدل إنشائه عند الاستيراد. تبقى قرارات صلاحيات البيانات في الخادم؛ حارس الصفحة وإخفاء الأزرار يحسنان تجربة الاستخدام فقط.

## ربط الصفحة

`js/items.js` مثال للفصل:

- `items/model.js`: تطبيع قيم النموذج، الفلاتر، الترتيب، وخانات التصدير.
- `items/view.js`: بناء خيارات القوائم وصفوف العرض، مع ترميز كل قيمة نصية أو سمة HTML.
- `items/service.js`: استعلامات المواد ومعالجة أخطاء الاستجابات في موضع واحد. يقبل العميل وأداة pagination من نقطة الدخول.
- `items/editor.js`: حالة نافذة التحرير وربط أحداثها، ومنع الإرسال المتزامن، والإبقاء على المدخلات عند الفشل.
- نقطة الدخول: تربط هذه الأجزاء بحالة الصفحة وأزرارها والتحديثات والصور.

مسارات `inventory/` و`orders/` و`preorders/` تتبع المبدأ نفسه، وتستفيد من أدوات `ui/` المشتركة عند تحميل المكتبات وتصدير الصور. تبقى بعض نقاط الدخول القديمة للتوافق أثناء الفصل التدريجي؛ لا تنقل ملفًا لمجرد تغيير اسم مجلد دون تحسين المسؤوليات.

## أدوات النصوص والأرقام

`core/text-utils.js` للأدوات النقية المشتركة، و`core/number-utils.js` لتحويلات رقمية صريحة. `import-review/normalize.js` يضيف سياسة تاريخ/ملفات الاستيراد. احتفظ بفارق مقصود بين تطبيع البحث وتطبيع الهوية؛ لا تستبدل أحدهما بالآخر دون اختبار.

القواعد:

1. القيم الفارغة لا تصبح صفرًا ضمنيًا.
2. العدد المطلوب صحيح لا يُقرّب بصمت من كسر.
3. التاريخ يُراجع كتاريخ فعلي، بما فيه أيام الأشهر والسنة الكبيسة.
4. يجب فصل فك تاريخ Excel الخاص بمكتبة القراءة عن منطق التاريخ القابل للاختبار.

## حدود العرض والأمان

- عند إنشاء عناصر من قيم خارجية، استخدم `textContent` أو `escapeHtml` لكل موضع إدراج نص أو سمة.
- لا يكفي تنظيف المسافات أو تطبيع الأرقام لحماية `innerHTML`.
- يجب أن يمر مسار معاينة الملف بمعايير الترميز نفسها المستخدمة عند عرض البيانات المحفوظة.
- مشاركة أدوات الصور أو التحويل لا تستدعي مشاركة جلسة أو صلاحية بين وحدات مستقلة.
- لا تُضمّن مفتاح Supabase الإداري في مصدر الواجهة. استخدام المفتاح العام لا يغني عن سياسات الخادم.

## الخدمات والأخطاء

كل خدمة تفحص `error` قبل استخدام `data`. فشل التحقق لا يُفسَّر كقائمة فارغة أو نتيجة نجاح. يمكن أن يكون فشل صورة اختيارية قابلًا للتجاوز، لكن فشل بيانات مطلوبة يجب أن يظهر كحالة مستقلة للمستخدم.

استخدم pagination عند قراءة قائمة قابلة للنمو. لا تنشئ `Promise.all` بلا حد على آلاف الصفوف. اجعل العمليات الجماعية ذات حدود واضحة، ولا تنقل معاملة متعددة الخطوات إلى المتصفح دون دراسة إعادة المحاولة والفشل الجزئي.

## الاختبارات

- **النماذج:** حالات صحيحة وحدود وفراغات وقيم غير صالحة، ومقارنة النتائج دون تعديل المدخلات.
- **العرض:** إدخال نصوص تتضمن وسومًا واقتباسات، والتحقق من عرضها كنص. اختبارات DOM للمسارات التي تستطيع تنفيذ HTML.
- **الخدمات:** عميل بديل قابل للتحكم؛ فحص تمرير الهوية وانتشار الخطأ دون قراءة قاعدة حقيقية.
- **التحرير:** الإرسال المتزامن، والفشل مع حفظ المدخلات، واستعادة حالة الأزرار.
- **المتصفح:** ربط أحداث ومعرفات HTML، وعرض أحجام الشاشة، باستخدام بيانات اختبار وجلسات بديلة.

اختبارات Node وPGlite تعمل محليًا. لا تشغّل اختبارات كتابة على قاعدة الإنتاج. وجود ملف SQL في `tests/` لا يعني دخوله تلقائيًا في `npm test`؛ يلزم مشغّل محلي صريح إذا أُضيف إلى مسار الفحص.

تجنب اختبار المنطق باقتطاع نص الدالة من المصدر وتقييمه بـ`new Function`. صدّر المنطق من الوحدة واختبر API مباشرةً. الاختبارات القديمة التي تعتمد على شكل المصدر تحتاج نقلًا تدريجيًا مع فصل الأجزاء المعنية.

## CSS والاعتماديات

ترتيب التنسيق: أساس عام، ثم تخطيط، ثم مكونات مشتركة، ثم ملف الصفحة. لا تضف override في ملف عام لمعالجة مشكلة محصورة في صفحة. استخدم tokens متسقة للألوان والمسافات، واحذف القواعد المتروكة بعد فحص المراجع.

وحّد عنوان استيراد الوحدة داخل التطبيق؛ المتصفح يعد URLs ذات query مختلف وحدات مختلفة. ثبت إصدارات الاعتماديات، وحافظ على ملفات الترخيص، وراجع الاعتماديات المحملة خارج npm أيضًا. تحدّث أدوات الجودة والاختبارات مع أي تغيير بنيوي، دون خفض القواعد لإخفاء خطأ جديد.

## تغييرات قاعدة البيانات

هذا الفصل للكود لا يستدعي تعديل المخطط أو البيانات. ملفات migrations الحالية تاريخ تراكمات فوق مخطط سابق؛ لا تضمن إنشاء قاعدة فارغة. أي تغيير لاحق للمخطط يحتاج فحصًا وتحققًا منفصلين ومراجعة صلاحيات، مع إبقاء أسرار الإدارة خارج المستودع.
